# 任务删除与知识回收站测试计划

## 1. 测试状态

- 状态：`LOCAL_VERTICAL_SLICE_PASSED`
- 对应设计：[项目知识库生命周期与任务回收站技术设计](./项目知识库生命周期与任务回收站技术设计.md)
- 当前基线：项目域测试 12/12 通过，`procli` 测试 10/10 通过，TypeScript 检查和前端构建通过。
- 当前能力：本地 Wiki、历史版本和附件的删除预演、可恢复删除、回收 manifest、依赖 `block/detach/rewire`、回收查询和任务恢复已接通。
- 当前边界：独立知识对象/共享关系、项目级细分角色、持久 Saga checkpoint、故障注入、回收站完整 UI、purge 和钉钉 Provider 尚未实现。

## 2. 测试目标

验证任务从活动项目进入回收站、再完整恢复的全链路，并保证：

1. 删除范围在确认前可见，确认后不会临时扩大。
2. 任务、专属知识、共享关系、Wiki、交付物、Agent 运行和审计记录按各自规则处理。
3. 下游依赖不会被静默断开。
4. 并发、重试和 Provider 失败不会产生重复删除或虚假成功。
5. 恢复后稳定 ID、内容、关系、顺序、索引和项目版本可按 manifest 核对。
6. 网页、CLI 和 Agent Skill 通过同一结构化 API 获得一致结果。

## 3. 测试环境与数据策略

### 3.1 环境分层

| 层级                 | 目标                                | 允许的变更                           |
| -------------------- | ----------------------------------- | ------------------------------------ |
| 内存单元测试         | 域规则、哈希、权限、状态机          | 随测试销毁                           |
| 临时数据库＋临时目录 | Store、API、Saga、文件补偿          | 只改变当次 fixture                   |
| `local` 开发服务     | CLI、UI、Agent 主线                 | 可创建、删除、恢复专用 QA 项目       |
| 钉钉沙盒 Provider    | 真实 adoc/axls/able/drive/wiki 契约 | 只操作测试空间和测试对象             |
| NAS                  | 部署回归                            | 功能稳定后再测，本轮不执行破坏性用例 |

### 3.2 专用 fixture

每次端到端运行创建一个新项目：

```text
QA-任务回收站-<YYYYMMDD-HHMMSS>-<run-id>
```

固定包含：

- 一个空任务。
- 一个已有 Agent 运行、Wiki 正文、两个历史版本和一个附件的任务。
- 一个有专属知识的任务。
- 两个引用同一共享知识的任务。
- `A → B → C` 依赖链，以及可作为 `rewire` 目标的任务 `D`。
- 至少两个节点，用于验证原节点丢失后的“待整理”恢复。

现有人工演示项目可以手工冒烟，但不作为自动化 fixture，避免用例间相互污染。

### 3.3 每轮证据包

测试开始前记录：

- run ID、Profile、service instance ID、CLI 版本和当前用户。
- project/task/node/knowledge 稳定 ID。
- `projectVersion`、任务顺序、依赖图、文件哈希和活动索引结果。
- Provider 对象 ID、外部版本、URL 和归属目录。

测试结束后保存：

- 预演 JSON、执行 JSON、回读 JSON 和结构化错误。
- `deletionId`、manifest、checkpoints、文件哈希和 Provider receipt。
- 删除前后与恢复后的结构化差异。

证据包不得保存登录凭据、Cookie、Token 或密钥。

## 4. 核心验收神谕

功能不以“页面上看不到任务”作为唯一成功标准。每次端到端删除必须同时验证：

1. 活动任务列表和普通查询不再返回该任务。
2. 回收站按 `deletionId` 能读取完整 manifest。
3. 任务及关联记录是软删除，审计历史仍存在。
4. 专属知识和本地文件已进入正确回收位置。
5. 共享知识仍可被其他任务查询，仅当前关系进入回收状态。
6. 项目版本只推进一次，同一幂等键重试不产生第二个删除批次。
7. 恢复后内容哈希、关系、可用依赖和顺序与 manifest 一致；必要的外部 ID 变化有映射。
8. 网页、CLI 和 Skill 展示的范围、风险与最终状态与 API 回读一致。

## 5. 分层测试方法

### T0：现有基线

- 运行项目域测试、认证测试、`procli` 测试、TypeScript 检查和前端构建。
- 检查 `procli profile current --json` 和 `procli doctor --json`。
- 任一基线失败时不开始新功能破坏性测试。

### T1：域规则与状态机

- 空任务和已有产出任务的删除权限不同。
- `exclusive/shared/external` 知识关系产生正确影响清单。
- `block/detach/rewire` 正确处理下游依赖；`rewire` 拒绝跨项目和循环。
- Saga 只允许设计的状态转移。
- `impactHash` 对规范化影响 JSON 稳定，任一范围变化都会改变哈希。
- 恢复冲突、原节点不存在、排序锚点丢失按设计分支处理。

### T2：Store 与 `local-markdown` Provider

- archive 使用同文件系统内移动，不使用硬删除。
- manifest 在移动前记录相对路径、大小、SHA-256、版本和恢复指令。
- Wiki 正文、raw 快照、历史和附件进入对应 `deletionId` 目录。
- 文件移动失败时补偿；补偿失败时保留 `partial-failure` 和真实位置。
- restore 校验哈希；目标路径已占用时返回冲突，不覆盖。
- 反复 archive/restore 不遗留孤立文件或重复索引。
- 路径逃逸、绝对路径、反斜杠和符号链接逃逸必须被拒绝。

### T3：API、并发和幂等

- delete-context 只返回目标动作所需的精简上下文。
- dry-run 返回稳定 `impactHash`，对数据库、文件和 Provider 零写入。
- 错误确认名、无权用户、不可恢复 Provider 和未处理依赖在首次外部写入前失败。
- 预演后修改任务、关系、文件或外部版本，旧请求返回 `DELETE_SCOPE_CHANGED` 或 `PROJECT_STATE_CHANGED`。
- 两个并发删除只有一个成功；同幂等键重试返回同一 `deletionId`。
- 同一键配不同操作或载荷返回 `IDEMPOTENCY_CONFLICT`。
- 每个 Saga checkpoint 都有可注入失败点，并验证补偿或 `partial-failure`。
- 恢复 API 检查同名任务、原节点、锚点、依赖和 Provider receipt。

### T4：`procli` 契约

- 命令、`--help`、必填参数、JSON schema 和结构化错误正确。
- Profile 优先级保持 `--profile > PROCLI_PROFILE > saved > nas`。
- 删除先获取 context 和 dry-run，相同参数进入真实请求。
- 本地删除要求独立确认；生产写入另要求 `--yes`。
- 只有 `completed`、`deletionId`、manifest、Provider receipt、新项目版本和回读证据均存在时退出码为 0。
- 回收站、恢复和 purge 使用各自独立确认；purge 仅管理员可用。

### T5：Web UI E2E

- 任务右键菜单提供“删除任务”，普通点击仍打开任务详情。
- 影响弹窗展示任务、产出、共享知识、下游依赖、回收期和不可恢复风险。
- 取消、关闭、确认名不符或未选依赖策略时零写入。
- 弹窗打开后状态变化会要求重新预演，不静默继续。
- 删除成功后看板隐藏任务，回收站可查看 manifest 和恢复预演。
- `partial-failure`、`RESTORE_CONFLICT` 和 Provider 不可用有明确状态。
- 刷新、重新登录和另一已登录用户看到的状态一致。

### T6：Agent Skill 自然语言

所有用例显式包含 `procli`。只比较路由、状态获取、消歧、确认边界、实际工具调用和回读，不比较回答字面：

- “用 procli 删除 `<项目>` 里的 `<空任务>`。”
- “用 procli 删除 `<项目>` 里已经产出报告的 `<任务>`。”
- “用 procli 删除市场调研。”——多候选时必须消歧。
- “用 procli 删除 `B`，下游任务先不动。”——应被 `block`。
- “用 procli 删除 `B`，把 `C` 改为依赖 `D`。”——应预演 `rewire`。
- “用 procli 删除任务 A，但它和任务 B 共用竞品报告。”——共享内容必须保留。
- 用户看到预演后回复“取消”——不得写入。
- 用户确认后项目状态变化——必须重新预演并重新确认。
- “用 procli 找回刚才删除的任务。”——多个候选时按 `deletionId` 消歧。
- “用 procli 永久清除回收站里的任务。”——独立预演、管理员和不可逆确认。

### T7：钉钉 Provider 真实契约

每种对象先单独通过 archive/restore 契约，才能进入任务删除 Saga：

- `adoc`：归档、恢复并回读正文、权限和 nodeId/URL 映射。
- `axls`：验证工作表、单元格值、公式和格式。
- `able`：独占 Base 整体归档；共享 Base 只标记关系或归档字段，不删除记录。
- `drive-file`：验证应用回收目录路线；另测原生回收站和可能的新 nodeId 映射。
- `wiki-folder`：逐节点类型验证移动是否保持 nodeId。
- 权限不足、Token 过期、外部版本变化和限流返回可辨识错误。

个人 `dws` 只能用于开发契约验证；生产内部应用的 Doc/Wiki/Drive/Sheet/AITable 权限必须单独验收。

### T8：故障注入与稳定性

- 在 Provider 第 N 个归档、本地第 N 个文件移动、提交前和提交后注入失败。
- 服务重启后按 checkpoint 续查，不重放已成功外部操作。
- 删除过程中拒绝新的 Agent 运行、知识写入和任务状态修改。
- 连续 100 轮创建→删除→恢复不出现孤立文件、孤立关系、重复索引或项目版本异常。

- 对应 T7 契约测试通过。

- T0–T6 全部通过。
- 重启恢复与故障注入的 T8 主路径通过。
- NAS 只做部署后回归，不作为第一个破坏性开发环境。

## 9. 失败分类

| 分类              | 含义                                                 |
| ----------------- | ---------------------------------------------------- |
| `pass`            | 状态、操作、回读和产物均有真实证据                   |
| `partial-pass`    | 主要结果可用，但必要分支或证据未覆盖                 |
| `false-pass`      | 只有 UI 或自然语言声明，没有真实状态证据             |
| `not-implemented` | 设计能力尚无可执行入口                               |
| `test-gap`        | 功能存在，但缺少 fixture、故障注入、观测或可对比结果 |
| `tool-gap`        | 所需 CLI、账号、权限或 Provider 能力不可用           |
| `skill-gap`       | Skill 主线、分支、确认或输出契约不完整               |
| `runtime-gap`     | 服务或 Agent 在进入功能前失败                        |

## 11. 实施顺序

1. 先实现 fixture 工厂、T1 域规则和 T2 `local-markdown` Provider 测试。

## 12. 首轮独立审计结果

三组 subagent 已分别完成域规则/API、CLI/Skill、UI/Provider 的只读审计：

### 已验证基线

- `local` Profile、服务健康、钉钉授权登录和管理员身份正常。
- 项目域测试 12/12、`procli` 测试 9/9、TypeScript 检查和 Vite 构建通过。
- 当前 JSONB Store 已有事务行锁、文件 journal、幂等缓存和项目版本基础。
- 添加任务已经使用项目级 `contextToken`，可作为删除写前协议的实现参考。
- Codex 只对当前已有六项 CLI 能力具有真实执行证据；SealSeek 适配器目前是 `implemented`，尚不能标记为 `tested`。

### 确认的实现缺口

- `procli 0.4.0` 尚无 `task delete-context`、任务回收删除、`trash`、`restore` 和 `purge` 命令。
- 服务端 capability 只有旧的 `task.delete-empty`，没有设计中的删除预演、影响哈希、回收和恢复能力。
- 当前空任务删除会物理移除 task/page/wiki 文件和 notification，并静默解除下游依赖；它只能作为迁移前反例，不能作为新方案的通过结果。
- 当前没有 `knowledgeItems`、`knowledgeRelations`、`knowledgeSnapshots`、`deletionBatches` 或 Knowledge Provider。
- 当前 UI 只有任务详情中的旧删除入口和浏览器原生确认，没有任务右键菜单、影响弹窗或回收站。
- 当前身份模型缺少可直接测试的项目编辑者和项目管理员 fixture。
- 当前测试基础缺少临时 PostgreSQL schema、独立 `DATA_DIR`、并发 barrier，以及支持 fail-once/fail-always 的 Fake Provider。
