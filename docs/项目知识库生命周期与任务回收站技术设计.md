# 项目知识库生命周期与任务回收站技术设计

## 1. 设计状态

- 状态：`READY`
- 目标：建立项目知识的初始化、写入、更新、删除、恢复、整理与查询契约，并以“删除任务及其产出后可完整恢复”作为第一个端到端用例。
- 目标平台：项目试验台服务、`procli`、Codex 与 SealSeek 的便携 Skill。
- 内容系统：本地/NAS LLM Wiki、钉钉知识库、钉钉文字文档、电子表格、AI 表格与钉盘文件。
- 实施约束：开发阶段先验证 `local-markdown` Provider；生产目标是以钉钉原生内容为人类协作权威源，LLM Wiki 为 Agent 编译检索层。

## 2. 核心决策

### 2.1 一个逻辑知识对象，三个职责层

```text
项目关系与治理层（PostgreSQL）
              ↓
人类协作内容层（钉钉原生文档/表格/AI 表格/文件）
              ↓
Agent 编译检索层（Markdown LLM Wiki）
```

三层表示同一个 `knowledgeItem`，不是三份可以各自修改的独立副本。

- 项目系统记录归属、稳定 ID、来源、版本、关系、权限、同步和回收状态。
- 钉钉原生内容用于员工阅读、协作、评论和权限管理。
- LLM Wiki 保存不可变来源快照、编译后正式页、索引和变更日志，为 Agent 提供稳定且可追溯的上下文。

### 2.2 内容权威源

每个知识对象显式记录 `authority`：

- `dingtalk`：生产默认；钉钉原文是权威源，Markdown 是只读编译产物。
- `local`：开发和本地预演；Markdown 正文是权威源。
- `external`：外部链接或无本系统写权的来源；系统只保存引用与获授权的快照。

任何写入端都必须先写权威源，按 ID 回读成功后再更新编译层。编译层不接受独立的人工修改。

### 2.3 钉钉内容类型路由

| 知识形态             | 默认类型      | 典型内容                                     |
| -------------------- | ------------- | -------------------------------------------- |
| 叙事、论证、结论     | `adoc`        | 市场分析、竞品报告、视觉方案、运营计划、复盘 |
| 计算型表格           | `axls`        | 成本、利润、预算、需要单元格公式的分析       |
| 持续增长的结构化集合 | `able`        | 商品清单、竞品库、用户访谈、样本、进度数据   |
| 原始证据与媒体       | `drive-file`  | 图片、PDF、视频、原始 Excel、导出数据        |
| 项目与节点容器       | `wiki-folder` | 项目目录、节点目录、回收站目录               |

生产环境使用一个企业级“项目知识库”空间，在空间中建立项目和节点目录。每个项目创建独立空间不作为默认策略。

## 3. I → S → O 合同

### I — Input

- 明确包含 `procli` 的项目知识或任务操作意图。
- 精确或可唯一解析的项目、节点、任务或知识对象。
- 写操作需要当前 Profile、身份、精简上下文、`projectVersion`、`contextToken` 和幂等键。
- 删除需要用户在查看真实影响清单后独立确认。
- 上下文、目标或权限含糊时，Skill 显示当前候选并请用户消歧。

### S — Strategy

```text
验证 Profile/身份
→ 读取结构化精简上下文
→ 解析稳定 ID 和内容关系
→ 服务端预演与影响清单
→ 权限与用户确认
→ 项目版本、外部版本和影响哈希复核
→ 按 Saga checkpoint 执行
→ 回读业务对象、外部对象与 LLM Wiki 索引
```

### O — Output

- 写入：返回项目/任务/知识稳定 ID、权威源位置、编译页、版本、同步状态和回读证据。
- 删除：返回 `deletionId`、删除范围、回收条目、保留的共享知识、下游依赖处置、可恢复截止时间、项目新版本和回读证据。
- 恢复：返回原 ID/新外部 ID 映射、恢复位置、重建的关系与索引、冲突和警告。
- 查询：返回结论、项目/节点/任务归属、钉钉原文链接、编译快照版本和时效性。

## 4. 项目 LLM Wiki 结构

```text
wiki/
├── AGENTS.md
├── SCHEMA.md
├── index.md
├── log.md
├── source-manifest.json
├── nodes/
│   └── <node-key>/index.md
├── tasks/
│   └── <task-id>/index.md
├── knowledge/
│   └── <knowledge-id>.md
├── raw/
│   └── <knowledge-id>/<source-version>.md
└── recycle/
    └── <deletion-id>/manifest.json
```

- `raw/` 只写新版本，不覆盖历史快照。
- `knowledge/` 是 Agent 使用的正式知识页，必须带来源、权威源版本和同步时间。
- `tasks/<task-id>/index.md` 是任务与多个知识对象的路由页，不再假设“一个任务对应一个正文文件”。
- `source-manifest.json` 只保存可移植的来源元数据，不保存凭据或作者机器路径。
- 内部链接使用稳定逻辑 ID；链接展示名可随标题变化。


### 5.2 `knowledgeRelations`

```json
{
  "id": "uuid",
  "projectId": "uuid",
  "knowledgeId": "uuid",
  "subjectType": "task|node|project|knowledge",
  "subjectId": "stable-id",
  "relation": "produced-by|references|derived-from|supports",
  "ownership": "exclusive|shared|external",
  "status": "active|recycled",
  "createdAt": "RFC3339"
}
```

`ownership` 决定任务删除时的动作：

- `exclusive`：随任务进入回收站。
- `shared`：只回收当前任务关系，知识本体保留。
- `external`：只删除引用，不尝试删除外部源。

### 5.3 `knowledgeSnapshots`

保存每次从权威源编译的不可变版本：`knowledgeId`、`sourceVersion`、`contentHash`、`snapshotPath`、`compiledAt`、`compilerVersion`、`status`。

### 5.4 `deletionBatches`

```json
{
  "id": "uuid",
  "scopeType": "task",
  "scopeId": "task-id",
  "projectId": "project-id",
  "state": "planned|snapshotting|external-archiving|local-recycling|committing|completed|partial-failure|restoring|restored|purged",
  "expectedProjectVersion": 12,
  "contextToken": "opaque",
  "impactHash": "sha256",
  "manifestPath": "wiki/recycle/<deletion-id>/manifest.json",
  "requestedBy": "member-id",
  "confirmedAt": "RFC3339",
  "retentionUntil": "RFC3339",
  "checkpoints": [],
  "warnings": [],
  "createdAt": "RFC3339",
  "updatedAt": "RFC3339"
}
```

### 5.5 现有对象扩展

- `task`：增加 `deletedAt`、`deletedBy`、`deletionId`、`deletionState`。
- `project`：知识、任务、关系、索引或回收状态变化时推进 `projectVersion`。
- `events`：历史审计不物理删除；删除后在普通任务视图隐藏，在回收站和审计视图保留。
- `runs`、`artifacts`、`notifications`、`measurements`：保留原 ID，通过 `deletionId` 进入回收范围，不从历史中硬删除。

## 6. Knowledge Provider 契约

项目服务调用逻辑 Provider，Skill 和 CLI 不感知具体钉钉命令。

```ts
interface KnowledgeProvider {
  inspect(ref: KnowledgeRef): Promise<RemoteObject>;
  create(input: CreateKnowledgeInput): Promise<RemoteObject>;
  read(ref: KnowledgeRef): Promise<KnowledgeContent>;
  update(ref: KnowledgeRef, input: UpdateInput): Promise<RemoteObject>;
  archive(ref: KnowledgeRef, target: ArchiveTarget): Promise<ArchiveReceipt>;
  restore(receipt: ArchiveReceipt): Promise<RemoteObject>;
  purge(receipt: ArchiveReceipt): Promise<PurgeReceipt>;
}
```

### 6.1 `local-markdown`

- 开发阶段的可完整测试 Provider。
- 使用同文件系统内的可恢复移动，不使用递归硬删除。
- 所有写入通过现有 file change journal 实现失败补偿。

### 6.2 `dingtalk`

- 生产环境默认 Provider。
- 服务端使用钉钉内部应用的正式 API 和秘密管理；开发与验证可以使用官方 `dws` 契约对照，不把个人 `dws` 凭证或本机路径打包进 npm。
- 知识库内节点优先移到预留“回收站”目录，保留 nodeId，不默认调用原生删除。
- 普通钉盘文件优先移动到应用回收目录；原生回收站恢复可产生新 nodeId，必须保存 ID 映射。
- AI 表格记录删除不可逆，任务回收默认把独占 Base 整体移入回收目录，或将共享 Base 内记录标记为“已归档”；不删除共享 Base 记录。

Provider 缺少 `archive + restore` 完整契约时，该知识类型不能进入普通删除流程，必须返回 `FEATURE_UNSUPPORTED`。

## 7. 知识生命周期

### 7.1 初始化

1. 创建项目 Wiki 规则、Schema、索引、日志和来源清单。
2. 生产 Provider 在企业“项目知识库”中创建项目目录、节点目录、项目索引文档和回收容器。
3. 保存所有稳定 ID 和初始版本。
4. 外部 Provider 不可用时，项目仍可创建，知识库状态为 `provision-pending`，可按 checkpoint 续跑，不重复创建空间或目录。

### 7.2 写入与更新

1. Skill 根据产出形态选择逻辑内容类型。
2. CLI 读取任务、已有知识和 Provider 精简上下文。
3. 服务端预演将创建或修改的权威源及关系。
4. 在权威源中执行写入，按返回 ID 和版本回读。
5. 新增不可变 `raw` 快照，编译或更新正式页。
6. 更新任务、节点和项目索引，追加 `log.md`，推进项目版本。
7. 返回权威源与编译层的双重回读证据。

### 7.3 整理与 Lint

整理任务覆盖：重复知识、孤立页、断链、缺少来源、钉钉链接失效、编译快照落后、归属缺失、过期与冲突内容。

合并知识必须保留 `derived-from` 和原始快照；整理不得通过删除原始证据来获得干净结构。

### 7.4 查询

```text
项目/节点/任务/类型过滤
→ 项目索引与查询路由
→ Markdown 正式知识全文检索
→ 按需读取相关来源快照
→ 快照过期时定向读取钉钉最新版本
→ 返回结论、归属、版本和可点击原文链接
```

初期使用 PostgreSQL 全文检索与结构化过滤；数量和语义检索需求经真实数据证明后再增加向量层。

## 8. 删除任务设计

### 8.1 权限

- 空任务：具有项目编辑权的成员可在确认后删除。
- 已有 Agent 运行或知识产出的任务：项目管理员或系统管理员可在影响清单确认后删除。
- 彻底清除：仅系统管理员。

### 8.2 删除预演清单

`task delete-context` 和 `task delete --dry-run` 必须返回：

- Profile、环境、项目、节点、任务、操作者权限。
- `projectVersion`、`contextToken` 和服务端计算的 `impactHash`。
- 任务状态、内容状态、排序位置与前后锚点。
- 活动、运行、通知、测量、Wiki 快照、交付物和外部知识对象数量。
- 每个知识对象的类型、所有权、其他引用、归档动作、恢复能力和风险。
- 依赖该任务的下游任务以及要求的依赖处理策略。
- 回收期、预计恢复方式和所有不可逆项。

`impactHash` 对影响清单的规范化 JSON 计算 SHA-256。执行时在数据库行锁内重新计算；项目版本、外部版本或范围变化时返回 `DELETE_SCOPE_CHANGED`。

### 8.3 下游依赖策略

存在下游任务时不允许默认删除。预演必须要求以下一种策略：

- `block`：拒绝删除，先修改依赖。默认。
- `detach`：删除下游任务对本任务的依赖，记录审计事件。
- `rewire`：把下游任务重连到用户明确指定的同项目任务，必须重新校验循环。

### 8.4 删除 Saga

```text
planned
→ snapshotting
→ external-archiving
→ local-recycling
→ committing
→ completed
```

1. 在行锁内验证项目版本、任务 ID、精确确认名称、`impactHash`、权限和幂等键。
2. 标记任务 `deletionState=deleting`，禁止新的运行、知识写入和状态变更。
3. 创建回收 manifest，包含任务快照、节点与顺序锚点、依赖、知识关系、内容版本、外部对象、文件哈希和恢复指令。
4. 按 Provider 归档独占知识；共享和外部知识只转移当前关系。
5. 将本地编译页和快照移入 `recycle/<deletion-id>/`，重建活动索引。
6. 执行已确认的下游依赖策略。
7. 设置任务、关联运行与交付物的 `deletedAt/deletionId`，更新项目版本并记录 `task.deleted` 事件。
8. 按 `deletionId` 回读任务、Provider 归档回执、manifest、索引和项目版本。

Provider 操作与 PostgreSQL/文件系统不具备跨系统原子性。每个外部步骤必须写 checkpoint 和幂等凭据。中途失败先执行已记录的反向移动；补偿失败则标记 `partial-failure`，保留真实终态并停止自动重试。

### 8.5 恢复

1. 按 `deletionId` 读取完整 manifest 和当前项目状态。
2. 检查同名活动任务、原节点、前后锚点、依赖对象和 Provider 归档对象。
3. 恢复 Provider 对象；节点 ID 变化时保存 old → new 映射。
4. 恢复任务原 ID、知识关系、运行、交付物和本地编译页。
5. 原节点不存在时放入“待整理”；原位置被占用时按最近存活锚点插入并返回警告。
6. 同名活动任务存在时返回 `RESTORE_CONFLICT`，不自动改名或覆盖。
7. 重建索引、追加 `task.restored` 事件、推进项目版本并回读。

### 8.6 保留与彻底清除

- 默认回收期：90 天。
- 首版不自动清理。
- 彻底清除为独立管理员能力，必须再次预演、精确确认对象和显式 `--yes`。
- 审计事件保留删除事实和哈希，不保留已按策略彻底清除的业务正文。

## 10. CLI 设计

```bash
# 知识库发现与初始化
procli wiki status --project "<project>"
procli wiki init --project "<project>" --dry-run

# 知识对象
procli knowledge list --project "<project>" [--task "<task>"]
procli knowledge get --project "<project>" --knowledge-id "<id>"
procli knowledge register --project "<project>" --task "<task>" ...
procli knowledge sync --project "<project>" [--knowledge-id "<id>"]
procli wiki query --project "<project>" --query "<question>"
procli wiki lint --project "<project>"

# 删除任务
procli task delete-context --project "<project>" --task "<task>"
procli task delete --project "<project>" --task "<task>" \
  --confirm-task "<exact task name>" \
  --dependency-policy block \
  --context-token "<token>" --impact-hash "<hash>" \
  --idempotency-key "<uuid>" --dry-run

# 回收与恢复
procli trash list [--project "<project>"]
procli trash get --deletion-id "<id>"
procli task restore --deletion-id "<id>" --dry-run
procli trash purge --deletion-id "<id>" --confirm-task "<name>" --yes
```

本地 Profile 的普通写入在用户意图已明确时执行；删除和彻底清除仍要求看过预演后的独立确认。生产 Profile 的写入另需 `--yes`。

## 11. Skill 主线

### 11.1 删除任务

1. 仅当请求包含 `procli` 时进入项目 Skill。
2. 用只读 CLI 唯一解析项目和任务。
3. 读取 delete context，不从对话记忆、网页或数据库直读推断范围。
4. 运行 dry-run，向用户展示任务、知识、文件、共享引用、下游依赖、回收期和风险。
5. 存在下游依赖时收集明确策略；存在不可恢复资源时停止普通删除。
6. 获得用户对该影响清单的明确确认。
7. 使用同一 Profile、任务 ID、上下文令牌、影响哈希和幂等键执行。
8. 只接受 `completed` 且任务、回收 manifest、Provider 回执、索引与项目版本全部回读通过的结果。

### 11.2 失败分支

- `PROJECT_STATE_CHANGED` / `DELETE_SCOPE_CHANGED`：重新读取上下文和预演，影响变化后重新请用户确认。
- `DEPENDENTS_EXIST`：请用户选择 `block`、`detach` 或精确 `rewire` 目标。
- `SHARED_KNOWLEDGE_RETAINED`：报告保留的知识和被移除的当前任务关系，不将其包装为完整内容删除。
- `FEATURE_UNSUPPORTED`：Provider 无可恢复归档契约，停止删除。
- `PARTIAL_FAILURE`：报告每个 checkpoint 的真实终态和所需管理员处理，不自动重试。
- 返回未知：只能以原幂等键恢复查询，不生成新删除请求。

## 15. 验收标准

### 确定性检查

- 删除 dry-run 不改变数据库、文件或 Provider 对象。
- 项目状态或外部对象版本变化后，旧预演必须被拒绝。
- 同一幂等键重试只存在一个 `deletionId`。
- 未确认、权限不足、下游依赖未处理、Provider 不可恢复时不发生删除。
- 共享知识仍可被其他任务查询，被删任务关系不再出现在活动索引。
- 删除后活动任务查询无结果，回收站可按 `deletionId` 读取完整 manifest。
- 恢复后任务 ID、内容、版本历史、交付物、知识关系和可用依赖与 manifest 一致。
- 部分失败保留 checkpoint 和真实资源位置，不重放已成功外部操作。

### 真实主线

1. 在本地验收项目创建一个任务，写入 Wiki 正文并上传附件。
2. 预演并确认删除，核对活动看板、查询索引、回收 manifest 和实际文件位置。
3. 恢复该任务，按 ID 回读任务、Wiki 正文、附件、历史、关系、排序和项目版本。
4. 对一篇专属 adoc 执行钉钉 Provider 的归档与恢复，检查原链接或 ID 映射、正文、归属和编译快照。

## 16. 已知缺口

- 钉钉内部应用访问 Doc/Wiki/Drive/AITable 所需的具体权限范围、企业管理员授权和服务端 Token 策略需在 Provider 实现前通过当前官方文档与真实内部应用校验。
- 钉钉知识库目录中不同节点类型的移动是否都保持 nodeId，需逐类型真实回归。
- AI 表格的“共享 Base 内记录归档”需预留统一归档字段；现有外部 Base 没有该字段时不得自动改表结构。
- 现有单行 JSONB 存储可用于本地垂直验证；知识数量、外部作业和多人并发增长后，需按本文实体契约拆分 PostgreSQL 表和 job/outbox 队列。
- 回收期、项目管理员角色和彻底清除审计保留期需在生产上线前形成企业策略。
